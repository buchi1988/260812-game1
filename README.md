# Dot Rush

みんなで同時に遊べるリアルタイム対戦ゲームです。アリーナを動き回って光るオーブを集め、90 秒でどれだけ得点できるかを競います。

Cloudflare Workers と Durable Objects だけで動きます。データベースも外部サービスも不要です。

## 遊び方

1. 名前とルーム名を入れて「ゲームに参加」
2. **WASD / 矢印キー**（スマホは**画面をドラッグ**）で移動
3. 水色のオーブで **+1 点**、金のオーブで **+3 点**
4. 90 秒たったら結果発表 → 8 秒後に自動で次のラウンド

同じルーム名を入れた人同士がその場で対戦相手になります。ヘッダーのルーム名をタップすると招待リンクがコピーされるので、それを配れば一緒に遊べます。1 ルームは 16 人までです。

## 動かす

```bash
npm install
npm run dev      # http://localhost:8787
```

複数のタブで開けば 1 人でも対戦の様子を確認できます。

```bash
npm test         # サーバー側の動作確認 (wrangler dev を自動で起動)
npm run typecheck
```

## デプロイ

```bash
npx wrangler login
npm run deploy
```

`https://dot-rush.<あなたのサブドメイン>.workers.dev` で公開されます。Durable Objects は無料プランでも使える SQLite バックエンドで作成する設定にしてあります (`wrangler.jsonc` の `new_sqlite_classes`)。

## 仕組み

```
ブラウザ ──WebSocket──┐
ブラウザ ──WebSocket──┼─→ Worker (ルーティング) ─→ Durable Object "PARTY"
ブラウザ ──WebSocket──┘                             ├ 全員の WebSocket を保持
                                                    ├ 20Hz でゲームを進める
                                                    └ 最高記録を保存
```

**ルームごとに Durable Object が 1 つ。** Worker は `idFromName(ルーム名)` で目的のインスタンスへ WebSocket を中継するだけです。Durable Object は世界に 1 つしか存在しないことが保証されているので、同じルーム名を入れた人は必ず同じインスタンス — つまり同じ試合 — に集まります。ゲームの状態がそこ 1 箇所にしかないため、ロックも同期処理も要りません。

**サーバーが唯一の権威です。** クライアントが送るのは移動したい向き (`dx`, `dy`) だけで、座標もスコアも送りません。位置の計算・当たり判定・得点はすべて Durable Object 側で行うので、クライアントを改造しても瞬間移動や不正な加点はできません。受け取った向きは長さ 1 に正規化されるため、速度を盛ることもできません。

**ゲームループは人がいる間だけ回ります。** 最初の 1 人が入ったときに `setInterval` で 20Hz のループを開始し、全員が退出したら止めます。誰もいない部屋で時間だけが進む、ということが起きません。WebSocket が繋がっている間 Durable Object はメモリ上に留まるので、状態をストレージに書き戻す必要もありません（部屋の最高記録だけは永続化しています）。

**表示はクライアント側で滑らかにします。** 20Hz の更新をそのまま描くとカクつくので、

- 他のプレイヤーは 110ms 前の状態を 2 つのスナップショット間で**補間**して描く
- 自分だけはサーバーと同じ計算式で**先読み**して、押した瞬間に動き出すようにする

先読みに使う速度や加速度は接続時に `welcome` メッセージでサーバーから配られるので、値がずれることはありません。

**先読みの補正は「同じ時点どうし」で比べます。** ここが操作の軽さを決めます。

サーバーから届く自分の位置は、必ず通信の遅れぶん過去のものです。これを「今いると思っている位置」と比べて寄せてしまうと、通信の遅れをズレと誤認して先読みを打ち消し、往復時間がそのまま操作の重さになります。

そこでサーバーは、入力に添えられた送信時刻から時計の差を測っておき、`me` メッセージで「**この位置はあなたの時計で何時に相当するか**」を返します。クライアントは自分の予測位置の履歴からその時点の値を引き、そことの差だけを直します。こうすると差として出るのは通信の遅れではなく、壁ぎわの丸めや他プレイヤーとの押し合いといった**本物のズレだけ**になります。補正を当てたら履歴も同じ量だけずらし、同じズレを二度数えないようにしています。

実測では、往復 90ms を挟んでも予測とサーバーの差は平均 2.2px に収まります（同じ条件で、今の位置と直接比べると 21px ずれます）。

**移動距離は刻み幅によらない式で計算します。** 速度は目標値へ指数的に追従させますが、その間の移動距離を「更新後の速度 × dt」で済ませると、20Hz のサーバーと 60fps のクライアントで進む距離が食い違います。解析解

```
k  = 1 - exp(-ACCEL * dt)
dx = 目標速度 * dt + (今の速度 - 目標速度) * k / ACCEL
```

を両方で使うことで、dt がいくつでも厳密に同じ位置になり、上の補正が本物のズレだけを見られるようになります。

### やりとりするメッセージ

| 向き | 種類 | 中身 |
| --- | --- | --- |
| → サーバー | `input` | 動きたい向き `dx`, `dy` と、送信時刻 `ts`（時計合わせ用） |
| → サーバー | `ping` | 往復時間の計測 |
| → クライアント | `welcome` | 自分の ID、アリーナのサイズ、物理パラメータ、最高記録 |
| → クライアント | `roster` | 参加者の ID・名前・色（入退室時のみ） |
| → クライアント | `state` | 毎 tick の位置・スコア・オーブ・取得エフェクト |
| → クライアント | `me` | 本人だけに、自分の正確な位置と、それが本人の時計で何時に相当するか |

`state` は 20Hz で流れるので、名前や色のような変化しない情報は `roster` に分けてあります。座標は整数に丸め、配列で詰めることで 16 人でも 1 通あたり数百バイトに収まります。`me` は宛先ごとに中身が変わるため別メッセージにしてあり、全員に配る `state` を太らせません。

## ファイル

| パス | 内容 |
| --- | --- |
| `src/index.ts` | Worker。`/api/ws` を該当ルームの Durable Object へ中継する |

| `public/index.html` | 画面の骨組み |
| `public/game.js` | 描画・入力・補間・先読み |
| `public/style.css` | 見た目 |
| `test/smoke.mjs` | サーバー側の動作確認 |

## 調整する

`src/game-config.ts` の値を変えるだけで手触りが変わります。

| 値 | 既定 | 説明 |
| --- | --- | --- |
| `ROUND_MS` | 90 秒 | 1 ラウンドの長さ |
| `MAX_SPEED` | 260 | プレイヤーの速さ |
| `ACCEL` | 45 | 操作の追従。大きいほどキビキビ動く。キーを離してから滑る距離は `MAX_SPEED / ACCEL` px |
| `ORB_COUNT` | 14 | 同時に出ているオーブの数 |
| `GOLD_CHANCE` | 0.14 | 金のオーブが出る確率 |
| `MAX_PLAYERS` | 16 | 1 ルームの定員 |
| `WORLD_W` / `WORLD_H` | 800 × 800 | アリーナの広さ（正方形にしてあるのは、横長のモニタでも縦持ちのスマホでも同じくらいの大きさで全体が見えるようにするため） |

アリーナのサイズは接続時にクライアントへ送られるので、変えたときにクライアント側を直す必要はありません。
