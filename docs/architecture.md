## 1. 全体像

```
ブラウザ ─┐
ブラウザ ─┼── WebSocket ──→ Worker ──→ Durable Object "PARTY"
ブラウザ ─┘                (中継のみ)     ├ 全員の WebSocket
                                          ├ 20Hz のゲームループ
                                          ├ 全プレイヤーとオーブの状態
                                          └ 部屋の最高記録 (永続化)
```

役割は 3 つに分かれています。

| 層 | 責務 | やらないこと |
| --- | --- | --- |
| Worker (`src/index.ts`) | ルーム名の検証と、対応する Durable Object への中継 | 状態を持たない |
| Durable Object (`src/game-room.ts`) | ゲームの全状態、20Hz のシミュレーション、配信 | 描画に関すること |
| ブラウザ (`public/game.js`) | 描画、入力の送信、補間と先読み | 得点や当たり判定の決定 |

静的アセットは Workers Assets が配信します。`public/` に一致しないパスだけが Worker に渡るので、`/api/ws` 以外のルーティングを書く必要がありません。

## 2. なぜ Durable Object なのか

リアルタイム対戦で難しいのは「全員が同じ 1 つの状態を見る」ことです。通常の Worker はリクエストごとに別のインスタンスで動きうるので、共有状態を外部（KV、D1、Redis など）に置き、競合を自分で捌く必要があります。

Durable Object はこれを構造で解決します。

**同じ ID のインスタンスは世界に 1 つだけ。** `idFromName("PARTY")` は決定的な ID を返し、その ID のインスタンスは全世界で 1 つしか存在しないことが保証されます。したがって同じルーム名を入れた人は、どの国から繋いでも必ず同じインスタンス — 同じ試合 — に集まります。

**単一スレッドで動く。** 状態はインスタンスのメモリ上にあり、同時に触るコードは他にいません。ロックもトランザクションも要りません。`this.sessions` という素の `Map` がそのまま真実になります。

**WebSocket が繋がっている間は生きている。** そのため、状態をストレージに書き戻す必要がありません。書いているのは部屋の最高記録だけです（`ctx.storage`）。

この 3 つのおかげで、ゲームサーバーの本体が 500 行程度に収まっています。

### インスタンスが置かれる場所

Durable Object は最初にアクセスされた地域の近くに作られ、以降そこに留まります。日本のプレイヤーだけで遊ぶなら日本近郊に置かれ、往復は数十 ms に収まります。逆に、地理的に離れた人が混ざると、遠い人ほど不利になります（[6. ネットコード](#6-ネットコード)の補正はこれを軽減しますが、なくすことはできません）。

## 3. ライフサイクル

### 接続

```
GET /api/ws?room=PARTY&name=たかし   (Upgrade: websocket)
  → Worker: ルーム名を /^[A-Z0-9]{1,12}$/ で検証
  → DO: 定員 (16) を確認、WebSocketPair を作って accept
  → welcome を送信、roster を全員に配信、ループを開始
```

Hibernation API (`state.acceptWebSocket`) ではなく通常の `ws.accept()` を使っています。Hibernation を使うとインスタンスが退避されうるため `setInterval` のゲームループが維持できないからです。接続が 1 本でも生きていればインスタンスは常駐します。

### ゲームループ

`ensureLoop()` が最初の 1 人の参加時に `setInterval(tick, 50)` を開始し、全員が退出したら止めます。無人の部屋で時間だけが進むことがありません。再び人が来たら新しいラウンドが最初から始まります。

1 tick でやることは順番に決まっています。

1. `movePlayers(dt)` — 入力に従って全員を動かす
2. `separatePlayers()` — 重なりを押し出す（O(n²)。16 人なら 120 回の比較で済む）
3. `collectOrbs(now)` — オーブとの当たり判定と加点
4. ラウンド時間の確認（終了なら結果フェーズへ）
5. `broadcastState(now)` — 全員へ配信

`dt` は実際の経過時間から計算し、100ms で頭打ちにしています。イベントループが詰まった直後に大きく飛ぶのを防ぐためです。

### ラウンド

```
playing (90 秒) ──→ result (8 秒) ──→ playing (スコアを 0 に戻して再開)
                       └ 最高記録を更新して ctx.storage に保存
```

最高記録の保存は `void this.ctx.storage.put(...)` で待ちません。ストレージの往復でゲームループを止めないためです。書き込みに失敗しても記録が 1 回残らないだけで、対戦には影響しません。

### 切断

`close` と `error` の両方で `onLeave` を呼び、セッションを回収して名簿を配り直します。送信に失敗した接続もその場で回収します（`sendRaw` の catch）。

## 4. 権威サーバー

クライアントが送るのは**動きたい向きだけ**です。座標もスコアも送りません。

```
クライアント → { t: "input", dx: 0.7, dy: -0.7, ts: 12345.6 }
```

受け取った向きは長さ 1 に正規化されます。

```ts
const len = Math.hypot(dx, dy);
if (len > 1) { dx /= len; dy /= len; }
```

このため、クライアントを改造しても以下はできません。

| やりたくなること | 防がれる理由 |
| --- | --- |
| 瞬間移動する | 位置はサーバーだけが計算する |
| 速く動く | 入力の長さが 1 に丸められ、速度上限は `MAX_SPEED` |
| 遠くのオーブを取る | 当たり判定はサーバーが行う |
| スコアを増やす | 加点はサーバーだけが行う |
| 壁の外に出る | 毎 tick でアリーナ内にクランプされる |

壊れたメッセージ（JSON でない、型が違う、巨大な値）は握り潰して接続を維持します。1 人の不正で部屋全体が落ちることはありません。512 文字を超えるメッセージは解析せずに捨てます。

**やっていないこと**: 認証はありません。ルーム名を知っている人は誰でも入れます。名前の重複も許しています。身内で遊ぶ用途を想定しているためで、公開の場で使うならルーム名を推測されにくくする（現在は未指定時にランダムな 4 文字）だけでなく、入室制限を足す必要があります。

## 5. 物理シミュレーション

### 速度

速度は目標値へ指数的に追従します。

```
k = 1 - exp(-ACCEL * dt)
v = v + (目標速度 - v) * k
```

`exp` を使うのは、フレーム間隔 `dt` が揺れても挙動が変わらないようにするためです。単純な `v += (target - v) * 0.3` だと、60fps と 30fps で追従の速さが変わってしまいます。

`ACCEL` は追従の速さそのもので、時定数は `1/ACCEL` 秒です。キーを離してから止まるまでに滑る距離は `MAX_SPEED / ACCEL` px になります。

| ACCEL | 時定数 | 滑る距離 | 感触 |
| --- | --- | --- | --- |
| 14 | 71 ms | 19 px | ぬるっと動いて滑る（初期値。重いと指摘された） |
| 25 | 40 ms | 10 px | 中間 |
| **45** | **22 ms** | **6 px** | キビキビ動く（現在） |

プレイヤーの直径が 36px なので、初期値では自分の半分の距離を滑っていたことになります。

### 移動距離 — なぜ解析解が要るか

速度が指数的に変化している間の移動距離を「更新後の速度 × dt」で済ませると、**刻み幅によって進む距離が変わります**。サーバーは 50ms 刻み、クライアントは 16.7ms 刻みなので、同じ入力を与えても加速中の移動量が食い違い、常にズレが生まれ続けます。

速度 `v(t) = 目標 + (v₀ - 目標)·e^{-a·t}` を積分すると、

```
∫₀^dt v(t) dt = 目標 * dt + (v₀ - 目標) * (1 - e^{-a·dt}) / a
              = 目標 * dt + (v₀ - 目標) * k / a        ← k は上と同じもの
```

`k` はすでに計算済みなので、割り算が 1 つ増えるだけです。この式なら `dt` がいくつでも厳密に同じ位置になり、サーバーとクライアントの予測が一致します。

```ts
// src/game-room.ts と public/game.js で同じ式を使っている
const k = 1 - Math.exp(-ACCEL * dt);
const tx = p.ix * MAX_SPEED;
p.x = clamp(p.x + tx * dt + ((p.vx - tx) * k) / ACCEL, PLAYER_R, WORLD_W - PLAYER_R);
p.vx += (tx - p.vx) * k;   // 位置を先に更新してから速度を更新する点に注意
```

### 当たり判定

- **オーブ**: 中心間の距離が半径の和より小さければ取得。総当たり（16 人 × 14 個 = 224 回）
- **プレイヤー同士**: 重なったぶんを半分ずつ押し返す。体で進路をふさげるのが面白いので残している
- **壁**: 毎 tick でクランプ

オーブの再出現は、他のオーブやプレイヤーに近すぎない場所を 12 回まで引き直して選びます（プレイヤーの目の前にタダで湧かないよう、プレイヤーからの距離は 0.7 倍に割り引いて評価）。

## 6. ネットコード

ここがこのゲームで一番作り込んだ部分です。20Hz の更新をそのまま描くとカクつき、素朴に補正すると操作が重くなります。

### 他のプレイヤー — 補間

受け取ったスナップショットを蓄え、**110ms 前の状態**を 2 つのスナップショット間で線形補間して描きます。1 つ分の遅れを許容することで、パケットが 1 通落ちても飛ばずに済みます。

### 自分 — 先読み

自分だけはサーバーの返事を待たず、同じ計算式でその場で動かします。押した瞬間に動き出すのはこのためです。使う `speed` と `accel` は接続時に `welcome` で配られるので、値がずれることはありません。

### 自分 — 補正（重要）

先読みした位置は、いつかサーバーの言う位置に合わせ直す必要があります。壁ぎわの丸めや他プレイヤーとの押し合いで、予測が外れることがあるからです。

**素朴にやると失敗します。** 届いたサーバー位置を「今いると思っている位置」と比べて寄せると、こうなります。

```
    自分の予測      ●────────────→ 今ここにいるつもり
    サーバーの返事  ●──→ (往復時間ぶん過去の位置)
                    ↑ この差を「ズレ」とみなして引き戻すと…
```

サーバーから届く位置は**必ず**通信の遅れぶん過去のものです。それを現在位置と比べれば、通信の遅れがそのまま「ズレ」として計上されます。20Hz × 20% で引き戻し続けると 0.5 秒ほどで先読みが打ち消され、往復時間がそのまま操作の重さになります。後述のシミュレーションでは、初期実装は往復 40ms で 74ms、往復 90ms で 91ms 遅れた位置を描いていました。

**同じ時点どうしで比べれば解決します。**

```
    自分の予測の履歴  ●───●───●───●───→ 今
                      ↑ この時点と比べる
    サーバーの返事    ●
```

サーバーは入力に添えられた送信時刻 `ts` から時計の差を測っておき、`me` メッセージで「**この位置はあなたの時計で何時に相当するか**」(`et`) を返します。クライアントは自分の予測位置の履歴からその時点の値を引き、そことの差だけを直します。差として出るのは通信の遅れではなく、本物のズレだけです。

```
サーバー側: offset = 到着時刻 - ts        (観測した最小値を追う)
            et = 今のtick時刻 - offset
クライアント: 誤差 = サーバー位置 - 履歴[et の時点]
            位置 += 誤差 * 0.2            (170px 超なら瞬間移動)
            履歴 += 誤差 * 0.2            ← これを忘れてはいけない
```

最後の行が要点です。補正を当てたら履歴も同じ量ずらさないと、直したはずのズレを次の補正でも数え、同じ補正が何度もかかります。

`offset` は観測した**最小値**を追いかけます（`Math.min(offset, current + 0.5)`）。遅れて届いた入力ほど offset は大きく出るので、最小値がもっとも汚染の少ない推定になります。回線が本当に遅くなったときのために、1 入力あたり 0.5ms ずつ上げる余地を残しています。

### 実測

実際の Durable Object に、実回線相当の遅延を人工的に挟んで接続し、予測とサーバーの差を測ったものです（`test/smoke.mjs` の「先読みの精度」が同じ測定を回帰テストとして行います）。

| 往復時間 | 同じ時点と比べる（現在） | 今の位置と比べる（初期実装） |
| --- | --- | --- |
| 0 ms | 1.6 px | 1.6 px |
| 40 ms | **1.6 px** | 9.9 px |
| 90 ms | **1.6 px** | 20.6 px |

現在の方式では誤差が**往復時間によらず一定**です。残る 1.6px は tick の粒度と回線の揺らぎによる床で、実用上は無視できます。初期実装の比例分が、そのまま毎回引き戻されていた量にあたります。

### 設計時の比較

実装前にクライアントとサーバーの計算を再現したシミュレータで比較しました。実効遅延は「理想（押した瞬間に最高速）より何 ms 遅れた位置が描かれるか」です。

| 方式 | 往復20ms | 往復40ms | 往復90ms | 40px のズレへの追随 |
| --- | --- | --- | --- | --- |
| 初期実装 | 58 ms | 74 ms | 91 ms | 520 ms |
| ACCEL のみ 45 に | 14 ms | 31 ms | 48 ms | 520 ms |
| + 解析解 + et 補正 | 14 ms | -3 ms | -19 ms | 520 ms |

最後の行が現在の実装です。負の値は理想よりわずかに先に描かれていることを意味しますが、これは加速中にサーバーが進む距離をクライアントが正しく再現している結果で、害はありません。**補正を無効にしたわけではない**ことは右端の列で確認しています。本物のズレには初期実装と同じ速さで追随します。

### 入力の送り方

向きを変えた瞬間の送信を待たせると、待たせたぶんがそのまま操作の重さになります。初期実装は一律 50ms 間隔で、切り返しに平均 25ms の純粋な待ちが乗っていました。

| 状況 | 送信間隔 |
| --- | --- |
| 大きく向きが変わった（キー操作） | 即座（最短 12ms） |
| 細かく変わり続ける（ドラッグ操作） | 33ms（30Hz） |
| 変わっていない | 100ms（時計合わせを兼ねる） |

無変化でも 100ms ごとに送るのは、`offset` の推定を新鮮に保つためです。

## 7. プロトコル仕様

すべて JSON テキストフレームです。`t` がメッセージ種別。

### クライアント → サーバー

#### `input`
```jsonc
{ "t": "input", "dx": 0.7, "dy": -0.7, "ts": 12345.6 }
```
`dx`,`dy` は動きたい向き。長さが 1 を超えるとサーバー側で正規化されます。`ts` は `performance.now()` の値で、時計の差の測定に使われ `me.et` として返ってきます。

#### `ping`
```jsonc
{ "t": "ping", "ts": 12345.6 }
```
`pong` でそのまま返ってきます。往復時間の表示に使うだけで、補正には使いません。

#### `rename`
```jsonc
{ "t": "rename", "name": "たかし" }
```
名前を変えます。制御文字は除去され、12 文字に切り詰められます。空なら「ゲスト」。

### サーバー → クライアント

#### `welcome` — 接続直後に 1 回
```jsonc
{
  "t": "welcome",
  "id": 3,                       // 自分のプレイヤー ID
  "world": { "w": 800, "h": 800 },
  "tickMs": 50,
  "playerR": 18, "orbR": 10, "goldR": 15,
  "speed": 260, "accel": 45,     // 先読みに使う物理パラメータ
  "roundMs": 90000, "resultMs": 8000,
  "best": { "name": "ゆい", "score": 42, "at": 1786489245408 }  // null の場合あり
}
```
物理パラメータを配ることで、クライアント側の定数がサーバーとずれることを構造的に防いでいます。

#### `roster` — 入退室と改名のときだけ
```jsonc
{ "t": "roster", "players": [ { "id": 3, "name": "たかし", "color": "#ff5c8a" } ] }
```
名前と色は滅多に変わらないので、毎 tick の `state` から分離してあります。

#### `state` — 毎 tick（20Hz、全員に同じもの）
```jsonc
{
  "t": "state",
  "ph": "playing",               // "playing" | "result"
  "tl": 45230,                   // フェーズの残り ms
  "best": { "name": "ゆい", "score": 42, "at": 1786489245408 },
  "p": [ [3, 412, 508, 7, 0] ],  // [id, x, y, スコア, 直近に得点したか]
  "o": [ [91, 233, 645, 1] ],    // [id, x, y, ゴールドか]
  "f": [ [233, 645, 1] ]         // この tick の取得エフェクト [x, y, ゴールドか]
}
```
配列で詰め、座標を整数に丸めることでサイズを抑えています。オーブの `id` は再出現のたびに新しくなるので、クライアントはこれを見て出現アニメーションを出します。

#### `me` — 毎 tick（本人だけに）
```jsonc
{ "t": "me", "et": 12345, "x": 412.3, "y": 508.1 }
```
`et` は「この位置はあなたの時計（`performance.now()`）で何時に相当するか」。`state` と違い宛先ごとに中身が変わるため別メッセージにしてあり、全員に配る `state` を太らせません。座標は小数第 1 位まで送ります（補正の精度のため）。

`et` は入力を 1 通も受け取っていないと計算できないので、その間このメッセージは送られません。

#### `pong`
```jsonc
{ "t": "pong", "ts": 12345.6 }
```

### エラー応答（HTTP）

| 状況 | ステータス |
| --- | --- |
| ルーム名が英数字 1〜12 文字でない | 400 |
| WebSocket へのアップグレードでない | 426 |
| 定員（16 人）に達している | 503 |
| `/api/*` の未知のパス | 404 |

## 8. 帯域と規模

16 人が同室で全員動き続けている状態での実測値です。

| 項目 | 実測 |
| --- | --- |
| `state` 1 通 | 平均 534 バイト（最大 554） |
| `me` 1 通 | 38 バイト |
| `roster` 1 通 | 839 バイト（入退室時のみ） |
| 下り（1 人あたり） | 約 11.2 KB/秒 |
| 上り（1 人あたり） | 約 1.8 KB/秒 |
| Durable Object の下り合計 | 約 179 KB/秒 |

2 人なら `state` は約 310 バイトです。

`me` を全員に配る `state` に混ぜず別メッセージにしたのは、宛先ごとに中身が変わると `JSON.stringify` を人数分やり直す必要があるからです。現在は `state` を 1 回だけ文字列化して全員に使い回し、38 バイトの `me` だけを個別に作っています。

**規模の上限は Durable Object が 1 インスタンスであること**から来ます。1 部屋 16 人は `MAX_PLAYERS` で決めた値で、CPU 的にはまだ余裕があります（当たり判定は 16 人で 224 回 + 120 回）。部屋の数はいくら増えても構いません。部屋ごとに別インスタンスなので、負荷は自然に分散します。

## 9. テスト

```bash
npm test        # wrangler dev を自動で起動して 28 件
npm run typecheck
```

`test/smoke.mjs` は素の WebSocket クライアント（ボット）を繋いで実際に遊ばせます。ブラウザを使わないぶん速く、サーバーの振る舞いを直接確認できます。

| 区分 | 確認していること |
| --- | --- |
| ルーティング | 静的配信、426、400、404 |
| 対戦 | 接続、名簿、色の重複、配信レート、得点、全員のスコア一致、めり込み防止、壁の内側 |
| 不正な入力 | 壊れた JSON、未知の種別、巨大な値を投げても接続と壁が保たれる |
| 退出 | 名簿からの削除、残った人への配信継続 |
| **先読みの精度** | 往復 90ms を挟んでも予測とサーバーの差が平均 5px 未満、かつ素朴な方式の半分未満 |
| 定員 | 16 人、17 人目の拒否、別ルーム、空き待ち |

「先読みの精度」は [6. ネットコード](#6-ネットコード)の設計が壊れていないことを守るためのもので、クライアントと同じ予測計算をするボットを人工遅延つきで走らせています。ここが落ちたら、操作が重くなる回帰が入ったということです。

ブラウザでの確認（3 画面を同じ部屋に入れ、キーボードとドラッグの両方で得点し、結果発表とスコアのリセットまで見る）は開発中に Playwright で行っています。ラウンド長を一時的に短縮する必要があるため、常設のテストには含めていません。

## 10. 調整できる値

`src/game-config.ts` にまとまっています。アリーナのサイズや物理パラメータは `welcome` でクライアントへ配られるので、変えてもクライアント側を直す必要はありません。

| 値 | 既定 | 効果 |
| --- | --- | --- |
| `WORLD_W` / `WORLD_H` | 800 × 800 | アリーナの広さ。正方形なのは、横長のモニタでも縦持ちのスマホでも全体が同じくらいの大きさで見えるようにするため |
| `TICK_MS` | 50 | シミュレーションと配信の間隔。下げると滑らかになるが帯域と CPU が増える |
| `MAX_PLAYERS` | 16 | 1 部屋の定員 |
| `MAX_SPEED` | 260 | 速さ |
| `ACCEL` | 45 | 操作の追従。滑る距離は `MAX_SPEED / ACCEL` px |
| `ORB_COUNT` | 14 | 同時に出ているオーブの数 |
| `GOLD_CHANCE` | 0.14 | 金のオーブが出る確率 |
| `ROUND_MS` / `RESULT_MS` | 90 秒 / 8 秒 | ラウンドと結果表示の長さ |

クライアント側だけの値は `public/game.js` の先頭にあります（補間の遅延 110ms、補正の強さ 0.2、瞬間移動の閾値 170px、入力の送信間隔）。

## 11. 既知の制約

- **地理的な公平性** — Durable Object は最初のアクセス地域に置かれるため、遠い参加者ほど不利になります。補正で操作の重さは解消できますが、他プレイヤーの表示遅れ（往復時間 + 110ms）は残ります。
- **認証がない** — ルーム名を知っていれば誰でも入れます。
- **スマホの縦持ち** — アリーナは正方形なので画面に収まりますが、上下に余白が出ます。全画面を使うには表示を 90 度回す必要があり、名前が横向きになるため採用していません。
- **1 部屋 1 インスタンス** — 1 部屋あたりの人数は Durable Object 1 つの処理能力が上限です。数百人規模にするなら、状態の分割か、当たり判定の空間分割が必要になります。
- **`state` の全量配信** — 全プレイヤーと全オーブを毎 tick 送っています。16 人・14 個なら問題ありませんが、規模を上げるなら差分配信や視界範囲での絞り込みが要ります。
- **時計のずれ** — 補正は `performance.now()` と `Date.now()` の差が測定中に一定であることを前提にしています。数分のセッションでは問題になりませんが、極端に長い接続では `offset` の再測定が要るかもしれません（最小値追従が 0.5ms/入力 で上向きに補正するので、実用上は自然に追随します）。
